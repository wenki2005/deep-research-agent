## 对报告真实性最关键的修复

现在的 evidence_coverage 主要表示“多少核心发现有一段逐字匹配的引用”。它没有证明引用与结论语义一致，更没有证明来源发布的信息本身为真。建议在界面拆成三项：

1. 来源登记率：被展示的来源是否真的来自本次工具调用。
2. 引文匹配率：摘录是否能定位到留存的源文本。
3. 主张支持情况：支持、矛盾、信息不足；标明自动判断或人工复核。

保留 confirmed 必须有独立判定规则，不能直接继承 Writer 的枚举输出。多个 URL 也不能自动等同于多个独立来源；转载同一篇报道需要合并来源关系。

对于零证据结果，合理的行为是交付“本次未取得足够证据”的可读结果，并说明实际搜索过哪些方向。不要在警告后保留“已确认”的原始稿。质量评估应奖励有根据的拒答，但不把它统计为成功回答了事实问题。

建议数据流：

研究问题 → 时间与实体范围 → 搜索/抓取 → 源文本快照 → 原子主张/逐条引文 → 支持关系校验 → 报告渲染

质量不够时应补检索或补抓取缺失证据。当前低覆盖率分支只让 Writer 对同一份笔记重新写一次，没有获得新证据，且会无条件替换首次结果。建议保留候选结果，只有质量改善才替换。

## 静态检查发现的其他改进方向（未做独立运行验证）

- **资料截断过早**：来源证据包最多取前 20 条、每条 900 字符；工具展示正文最多 1400 字符，网页抽取最多 6000 字符。结尾的关键证据可能被截掉。应按问题检索文本片段并保留偏移位置，而不是只取开头。
- **摘要与正文没有区分**：Tavily 只读取 content，没有请求 include_raw_content；普通搜索把非空 content 当成不再抓取的依据。摘要可以作为搜索线索，但不应在 UI 中统一描述为“已读全文”。
- **事件时间与检索时间混用**：所有研究都被指示优先最近一两年，容易缩窄历史事件的查询范围。今天的日期、事件发生日期、报道发布日期应分别记录。历史原始报道与近期进展可以并行搜索。
- **中文搜索提示需要修正**：提示词把“Tavily 拒绝纯中文”当作通用规则。官方当前文档支持语言选项，并建议 query 与 language 一致；局部请求失败应按状态码和错误分类处理，不应当成语言禁令。
- **记忆质量没有准入门槛**：runner.py:247 在启用记忆后直接存整份报告；memory.py 只记录标题和创建日期，没有核验等级、证据快照或有效期。未核实信息可能影响后续规划。建议历史稿仅作线索，重新检索后才能作为本次证据。
- **缺少可重放审计**：来源注册表在内存中，save_report 主要保存 Markdown。建议保存脱敏的 run_id、查询参数、来源快照/哈希、抓取时间、校验理由、失败原因；这样才能判断“搜索没找到”还是“模型没引用”。
- **API 尚无真正异步任务状态**：task_id 在研究请求内部生成，客户端仍等整轮研究完成。建议补 queued/running/completed/failed/cancelled、进度查询与总超时，之后再考虑队列和恢复执行。
- **并发与命名**：查询使用 gather，但缺少任务级总时限/并发预算；同一秒、同名报告的文件名可能碰撞。建议有界并发、部分失败保留、UUID 文件名。
- **版本管理尚未隔离运行数据**：git ls-files 确认 memory/chroma.sqlite3 和若干生成 PDF 已受 Git 跟踪；.gitignore 不会自动取消已跟踪文件。本轮未改动这些文件，也未移除索引。发布整理时应另行处理并保留本地文件。
